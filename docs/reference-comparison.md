## 1. 最重要的一条：空间划分的尺度必须 ≥ 判定距离

四个项目里**有两个踩过同一个坑**，本项目是第三个：

| 项目 | 格子/邻域尺度 | 实际判定距离 | 后果 |
| --- | --- | --- | --- |
| **本项目**（历史） | 格子边长 50 | 大球 `r_a+r_b` = **107~150** | 要深深重叠才判定成碰撞：一帧推开几十格（突兀）、"贴上走一段才触发" |
| **战斗模拟** | 格子 5（3×3 邻域 = 15） | `attack_range` = **20** | 文档自己承认漏检："理论上敌人在 20 像素范围内可能在邻域之外……**如果出现漏检，下一帧会因为位置变化而补上**" |
| **商业版** | 不用格子 | — | 直接收大球下标 + 双重循环（`ProcessBigBallCollisions`） |
| **僵尸 / Boids** | 固定网格 + 每格采样上限 | — | 软分离力，不做硬碰撞，漏判后果轻得多 |

**正确公式**（战斗模拟 `docs/03-spatial-hashing.md:218` 的原文）：
> 对于半径 R 的圆形查询区域，使用边长为 `2×ceil(R/格子边长)+1` 的方形邻域可以保证不遗漏任何目标。

**另一条更省事的分工**（战斗模拟 `CPUBattleOrca.cs:47` vs `CPUBattleMeleeJobCs.cs:250`）：
**筛选半径要远大于真实碰撞半径** —— 先用一个宽松的半径（`orca_radius`）收候选，
再用真实半径（`combinedRadius = 双方半径之和`）精确建线。
把这两件事分开，空间结构的尺度就不会被"最大的那个球"绑架。

**本项目的处置**：不用空间划分了，直接两两枚举大球。
105 对/帧（10~15 颗球）比维护任何空间结构都快，而且**精确、不会漏判** ——
和商业版同一个做法。`Game/SpatialHash.cs` 已删除。

## 2. 连续碰撞检测（CCD）：三家都不做

- **商业版**写了扫圆—抛物线求根（`CheckMovingSpheresIntersect:678`、`MovingCircleRectIntersect:518`），
  但**两处都零调用**，实际路径里的注释是"静态碰撞检测（**去掉连续碰撞检测**）"(`:756`)；
  `PreviousPositions` 只写不读。
- **战斗模拟 / 僵尸**：定步长 + 静态重叠判定，靠固定步长把单步位移压小。
- **本项目**：单步位移 `90 ÷ 60 = 1.5` 格，而大球半径 53~75 —— 位移只有半径的 2~3%，
  实测"碰撞发生时的重叠量"≤ 2.6 格，肉眼看不出穿插。**不做 CCD 是对的。**

## 3. 分离与冷却：三种写法，本项目取中间

| 项目 | 重叠怎么处理 | 冷却 |
| --- | --- | --- |
| 商业版 | **只推开重叠量的 5%**（`overlap * 0.05f`，`:815`）+ 完全弹性交换法向分量 | 碰撞后 **0.4 秒**（`:832`），新球 1.0 秒 |
| 僵尸 | 软力：按重叠比例给力（`pushStrength = overlap/comfort * max`）、`totalForce /= collisionCount` 平均化、再钳一个**最小推力下限**（`Entity.cs:192-273`） | 每个僵尸 1333ms 墙钟冷却 |
| Boids | 三条力各自归一化再加权（权重 2/2/5，`BoidsDemo.cs:68-90`） | — |
| **本项目** | 重叠量**对半推开**，但**每帧封顶 6 格** | 敌对大球 **0.4 秒**（对齐商业版） |

取舍理由：
- 商业版的 5% 轻分离是**为深度重叠擦屁股** —— 他们的判定本来就可能很晚。本项目判定准了
  （重叠 ≤ 单步位移），所以可以老实推开，不需要靠"慢慢蹭"。
- 封顶 6 格是**兜底**：正常重叠 ≤3 格碰不到它；万一出现深度重叠（出生即重叠、角落堆叠）
  也不会一帧瞬移 —— 这正是用户反馈的"突兀"。
- 冷却用来把"**一次接触**"和"**一帧**"解耦：擦身而过会连续几十帧重叠，逐帧扣能量会把
  一次接触算成几十次。

## 4. 本项目**不适用**的借鉴项（查过，但对这个设计无效，写下免得重复调研）

| 参考做法 | 出处 | 为什么不适用 |
| --- | --- | --- |
| 大球速度钳制 + 每帧兜底"确保没有球静止" | 商业版 `EnsureSpeedInRange:926`、`EnsureAllBigBallsMoving:967` | 那是**可变速度**模型（80~150）才需要的兜底。本项目所有球速度恒定（`BallSpeed=90`），不存在静止或近零速度。 |
| 撞墙/踩格加防抖门槛（速度夹角 ≥30°、原速 ≥3） | 商业版 `:294-306` | 那是给"撞墙计数 / 逐格反弹"用的去抖。本项目大球**只跟地图边框**反弹一次，且不按反弹计数。 |
| 多格法线累积后归一化、单次反弹 | 商业版 `:410-421` | 本项目大球不跟格子做物理反弹（压过格子只是涂色 + 扣能量），没有"一帧压多格要不要弹"的问题。 |
| 尺寸 = 碰撞次数（撞墙 +1、被敌球 −1） | 商业版 `UpdateBigBallSizeFromCollisionCount:879` | 不可预期、注释与代码还不符（注释 16~200、代码实际 16~120）。本项目"能量决定尺寸"更自洽：尺寸 = 剩余预算的可视化。 |
| 8Hz 逻辑 + 60Hz alpha 插值（含累加器封顶防螺旋死亡） | 僵尸 `GameManager.cs:140-152` | 那是**服务端权威 8Hz** 的架构权衡。本项目规模小、模拟本来就 60Hz，已经用累加器 + `MaxStepsPerFrame=4` 防螺旋，没必要降频。 |
| GPU 分箱 / 前缀和（bin sort） | Boids `BinPrefixSum.glsl:15` | 15 颗大球用 O(n²) 更划算；且那份实现是 `for(i=0;i<=index;i++)` 的 O(bins²) 串行前缀和、`barrier()` 的内存可见性也没有保证。 |
| 每帧 `new float[N*12]` + 每帧 `ImageTexture.CreateFromImage` | 僵尸 `RenderingManager.cs:354,400`、`DropManager.cs:78` | **反面教材**：30000 实例 ≈2.8MB/帧 的分配，全仓无对象池。本项目复用同一个 `_ballBuffer` + 整块写 `MultiMesh.Buffer`，不要往这个方向退。 |
| GPUParticles2D + 数据纹理（两个商业项目最终都走这条） | 僵尸 / Boids | 那是为了画**带图集帧动画**的单位。本项目是纯色圆（着色器现画），MultiMesh 整块写缓冲更直接、更省。**不要被"商业项目都这么做"带偏。** |

## 5. 并行与数据布局：本项目已经对齐

- **战斗模拟**的"并行只读枚举 + 串行收口"（`CPUBattleSpatialHash.cs:98-111`：
  并行分块求和 → 宿主串行算前缀 → 并行落地；注释给了 9.24ms → 0.28ms 的收益）
  和本项目 `UpdateBalls` 的形态一致（并行填实例缓冲 + 串行写共享格子）。
- **它的调度铁律**：任务数必须固定 O(核数)，不能随元素数走 ——
  `docs/CPU-百万同屏-现状沉淀.md:281` 记录"1M 个逐元素任务光调度就 140ms，
  改成 64 个区间 IJob 后 328ms → 11ms"。
  本项目 `Parallel.For(0, stripes)` 里 `stripes = min(ProcessorCount, count)`，
  **符合这条铁律**；新增并行时照这个来。
- **状态/组件列（SoA）新增一个数组，所有搬移路径都要同步**：
  商业版的 `RemoveBalls` 交换了 7 个数组却漏了 `CollisionCounts`（`:999-1005`），
  导致"尺寸张冠李戴"。本项目新增 `_clashCooldown` 时已同步 `Spawn`、`Compact`、`KillTeam`
  三条路径 —— **这是每次加 per-ball 数组时必查的清单**。

## 6. 一句话总结

| 维度 | 结论 |
| --- | --- |
| 空间划分 | **尺度 ≥ 判定距离**；本项目干脆两两枚举（商业版同款） |
| CCD | 三家都不用；本项目单步位移只占半径 2~3%，也不需要 |
| 弹开 | 等质量弹性（交换法向分量）三家用的是同一套 |
| 防"黏/突兀" | 冷却（0.4s，对齐商业版）+ 判定要准 + 分离封顶 |
| 渲染 | 本项目"MultiMesh 整块写"比两个商业项目的 GPUParticles2D+图集更适配纯色圆 |
| 并行 | 任务数固定 O(核数)；SoA 新增列必须同步所有搬移路径 |
