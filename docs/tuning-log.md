# 调参实测记录与踩坑清单
> 这些内容是**实测出来的**，不是推测。数字环境：1000×1000 地图 / 8 队 / 60Hz 模拟 /
> RTX 4060 Laptop。改参数前建议先读一遍，能省掉重新试错的时间。
>
> 放在这里而不是代码里，是因为它已经长到会淹没类声明；代码里只留最关键的几行。
>
> 参考项目（商业版同题材 / 战斗模拟 / 海量实体）的横向对比见 **`docs/reference-comparison.md`**。

## 1. 性能

| 项 | 实测 |
| --- | --- |
| 常规人口 ~2800 | 模拟约 0.4 ms/步，FPS 360+ |
| 8000 颗满载 | 模拟 2.2 ms/步（染色 1.15 + 碰撞 0.95 + 其他 0.13），FPS 190-230 |

**`csproj` 里开 `Optimize=true` 是至今最大的一笔优化，单项快 2.5 倍。**

原因是 Godot 从编辑器或命令行运行游戏时用的是 **Debug 配置**，而 Debug 下 Roslyn 默认
`<Optimize>false</Optimize>` —— IL 完全不做优化（小方法不内联、循环不展开、局部变量不提升）。
对一个每帧跑几百万次数组访问的模拟来说这是纯浪费。同一负载对比：

| 阶段 | 优化前 | 优化后 | 提升 |
| --- | --- | --- | --- |
| 染色 | 3.2 ms/步 | 1.15 | 2.8× |
| 碰撞 | 1.9 ms/步 | 0.95 | 2.0× |
| 其他（基地/门/经济） | 0.5 ms/步 | 0.13 | 3.8× |

> 在打开它之前记录的所有性能数字，都是在未优化 IL 上测的，偏低约 2.5 倍。

### 已并行的三处

1. 调色板转换（按行分片，天然无写冲突）
2. 弹珠层缓冲填充（按球分片，每颗球只写自己那几个 float）
3. 碰撞枚举（按球分片 + 串行应用）

### 仍未并行：染色

它是现在最大的单项，但**不能直接并行** —— 它同时改 `owner` 和 `strength` 两处共享单元格，
并发写必然丢更新，而且两个字段会变成互相矛盾的状态（格子显示是 A 队、防御值属于 B 队）。
要并行得改成"按网格区域切分、跨界串行兜底"，或"每线程记录变更、最后串行合并"
（后者算过：8000 颗球 × 每球几十格 = 几十万条记录，写入量接近染色本身，不划算）。

### 其他已确认的性能事实

- **`MultiMesh.Buffer` 赋值是整块上传**，`VisibleInstanceCount` 只控制画几个、**不省上传**。
  缓冲长度 = `MaxBalls × (1 + TrailGhosts) × 步长`。所以拖尾会把上传量乘倍数，
  `MaxBalls` 也因此从 20000 降到 8000。
- 逐实例 `SetInstanceTransform2D`/`SetInstanceColor` 每颗球两次托管↔引擎调用，
  1 万颗要 1.9 ms；整块写 Buffer 只要 0.14 ms。
- `Image.SetPixel` 逐格写极慢（社区实测 1024×1024 逐帧写掉到 15 FPS）；
  100 万格用"调色板 LUT + 批量 `SetData`"是 3.3 ms（顺序）/ 0.8 ms（并行）。

## 2. 踩过的坑（改参数时别再踩）

### 大球压进敌境（原来的"释放 / Release"已按需求整体删除）

- **没有"一次性爆炸"了。** 大球压进敌境是**逐格磨过去的**：每步只对**新盖到**的格子
  收 `cellCost`，所以烧钱速度 = `盘宽 × 速度 × 每格成本`，而不是 `盘子面积 × 每格成本`。
  盘子 48、速度 1.5 格/步 ⇒ 每步约 144 格（约 8640 格/秒）。
- **⚠ 判定宽度是 48，不是画出来的环。** `Disk.MaxRadius = 48` 会把涂色盘夹住，
  而大球的视觉半径是 **50~100** —— 环外侧那一圈不在判定内（14.1K 的球画半径 62.6、
  只涂 48）。这是旧版"释放爆炸半径 40"留下的历史遗留，改 `Disk.MaxRadius = BallSwarm.MaxRadius`
  即可对齐（代价：最大盘 7250 → 31400 格，每步成本翻倍、推进深度减半）。
- **⚠ 历史上踩过的三个坑（代码删了，教训留着）：**
  1. 判定必须夹在"移动之后、染色之前" —— 染色会把球脚下那格变成自己的颜色，
     放在染色之后判定，永远问不出"踩在敌境上"。
  2. 判定要用**整个涂色盘**，不能只看球心那一格 —— 半径 48 的大球压在边界上时，
     球心还在自家地盘、盘子另一半已经盖住敌境。
  3. 一发打完**必须跌到门槛以下**：只按比例抽 60% 的话，30000 能量的球抽完还剩 12000
     仍然过线，于是每一步都再释放一次（30000→12000→4800→1920），三步把自己打空。
- **想让球变大不要靠抬高晋级门槛。** 攒到很高能量的球同时只有个位数
  （实测门槛 16000 时全图只有 0~3 颗过线）。要做大球请调 `BigMinRadius` /
  `BigMaxRadius`（大球档的半径范围）或 `BigBallEnergy`（晋级门槛）。

### 运动

- **弹珠必须是"近乎直线滚动 + 撞墙反弹"，不能是随机游走。** 曾经用 `TurnRate=0.8`
  做随机游走（方向每 1.25 秒完全随机化），球全缩在出生点打转，既不铺领土也不减员。
  当时的补救是加一个"远离基地"的外推力硬赶它们出去，结果画出放射状辐条。
  把转向率降到 0.15、删掉外推力，行为立刻对齐同类游戏。
  **⚠ 现在 `TurnRate` 只作用于小球**：大球是"保龄球"，出膛定死一个方向，一路直推，
  只在撞墙 / 撞球时改向（见"大球：随机能量 + 直线横推"）。
- **贴墙被顶回去**：`BounceOffWalls` 的镜面反射本身没错，是外推力在球贴墙时一直指向墙内、
  把它按在边界上磨。删掉外推力后这个问题自然消失。

### 渲染

- **`Viewport.UseHdr2D = true` 下，2D 纹理是按线性值显示的。** 这不是 bug 而是既有观感，
  但很容易误判：调色板里写的绿是 `(16,114,31)`，屏幕上实际是 `(1,21,52)` 那一档 ——
  因为采样时做了 sRGB→linear。**实测基线（无着色器）**：蓝 `(18,76,121)` → 显示 `(1,21,52)`；
  黄 `(123,108,10)` → 显示 `(55,42,0)`。
  曾经因为"加了边界辉光后觉得地图变亮了"而给着色器加了一步 `srgb_to_linear`，
  结果整张图变得过暗 —— **那是错的**。引擎在**采样时**转、输出时不转：
  让着色器输出常量 `0.5`，实测读回 `0.529`（只有辉光的几个百分点误差）。
  所以自定义着色器里采样 `TEXTURE` 后**原样输出**即可，与默认着色器逐字节一致。
  排查这类问题不要靠肉眼比截图，**用 `System.Drawing` 采样像素对比基线**。
- **球看起来会比几何尺寸大很多，那多半是辉光，不是球本身。** 辉光的模糊是**屏幕空间**的，
  光晕大致是固定像素大小 —— 球再小球看上去也是一团差不多大的光斑，**大小差异会被辉光抹平**。
  一度以为"白球太大、描边太粗"，真正的原因在这。收紧办法（都在 Environment 资源里）：
  `glow_intensity` ↓、`glow_bloom` ↓、`glow_hdr_threshold` ↑、`glow_hdr_scale` ↑、
  `glow_hdr_luminance_cap` ↓（把过亮区域截断，直接减少光晕能量）、
  以及把高位 `glow_levels/3..7` 置 0（只保留小模糊层级）。
- **排查渲染问题时记得先看镜头周围有什么。** 有一次把镜头怼到一颗球上放大 10 倍，画面几乎被
  一团糊住，一度以为是辉光失控 —— 其实大半个屏幕是被一个**增殖门**占据的
  （半径 55 格 × 10 倍缩放 = 1100px，比 1280×720 的视口还大）。
- **⚠ 手写 MultiMesh 缓冲必须在启动时自检布局 —— 这类错误是静默的。**
  引擎不报任何错，只是画出来不对。本项目栽过两次：`use_custom_data` 打开后步长 12→16，
  而颜色槽用"步长 − 4"去推，结果写到自定义数据槽上，**整层球一颗都看不见**。
  做法抄自 `ComputeShaderBattleSimulation/CPUBattle/Scripts/CpuMultiMeshInit.cs`
  的"列序/stride 契约探针"：**先用引擎自带的 setter 写一个已知值，回读 `Buffer` 逐 float 比对**，
  和代码里假设的偏移对不上就直接报错。见 `GameRoot.VerifyBallBufferLayout`。
  实测两种错法都能抓到：改偏移连带改步长 → 越界分支；两个槽互换而步长不变 →
  逐 float 比对分支（逐条报出"哪个槽、读到什么、期望什么"）。
- **写入契约：每次整块写 Buffer 之前，先调一次实例级 setter。** 见
  `GameRoot.MarkBallBufferDirty`（0 号哨兵放到远处 + 1 号退化，抄自
  `CpuMultiMeshInit.SetupIdentityBuffer`）。
  ⚠ 两边上下文不同，调用时机也不同：那边位置存在纹理里、实例缓冲**只写一次**，所以 setter
  只在初始化调一次；本项目每帧整块重写缓冲，就**每帧调一次**（`UpdateBalls` 里 `Buffer` 赋值前）。
  代价可忽略 —— 只有 2 次托管↔引擎调用（哨兵 + 退化），和"逐实例 setter"是两回事，
  后者对 MaxBalls 颗球才是每颗两次调用（实测 1 万颗 1.9ms，整块写 0.14ms）。
- **顺带澄清：实例级 setter 不是"缓冲能上传"的前提。** ComputeShaderBattleSimulation
  用 GPU 缓冲回读做过对照实验，跳过 setter 直接写 `MultimeshSetBuffer` **依然成功上传**。
  那里真正修的是另一个坑：直接调 `RenderingServer.MultimeshAllocateData` 会让 C# 侧
  `MultiMesh.InstanceCount` 属性停在 0，实例级 setter 被边界检查拒绝
  （`Instance index out of bounds`）。**本项目没这个问题** —— 我们走的是 resource 属性
  （`_ballMesh.InstanceCount = ...`），属性与引擎状态是同步的。
- **`MultiMesh.Buffer` 的布局是「变换 → 颜色 → 自定义数据」**，颜色槽偏移固定是 8
  （2D 变换占 8 个 float），不能用"步长 − 4"去推。详见上面那条自检的说明。
- **`MultiMesh.Buffer` 的长度必须严格等于 `InstanceCount × 步长`，否则 Godot 直接拒绝赋值、
  整层球一个都不显示。** 也不要靠读 `Buffer.Length` 反推步长：未赋值时长度可能是 0，
  被兜底值掩盖后长度就对不上。
- **⚠ 编辑器开着的时候，它会用自己的内存副本覆盖整个 `.tscn`。** 实测改好的
  `use_custom_data`、`glow_bloom`、`glow_levels/*` 都被改回去过，而且没有任何提示。
  所以**功能性的节点/资源配置不要只写在场景里，要在代码里强制一遍**
  （见 `GameRoot.AllocateBallBuffer` / `ConfigureMaterials` / `BuildMap`）。
- **2D 下的 `material` 要挂在 `MultiMeshInstance2D` 节点上**（`CanvasItem.material`），
  挂在 `QuadMesh` 资源上无效（实测整层不显示）。
- **canvas_item 着色器拿不到 MultiMesh 实例的真实缩放**，所以"是不是大球"只能 CPU 端算好
  传进来。实例的 8 个 float 分配见 `Disc.gdshader` 顶部注释：
  颜色 rgb = 阵营色、颜色 a = 透明度、自定义 x = 形态、自定义 y/z = 形态参数。
- **脚本的 `.tscn` 节点引用需要 `node_paths=PackedStringArray(...)` 元数据**，
  否则 Godot 不会把 `NodePath` 解析成节点对象，字段是 null。
- **拖尾不该用叠圆做。** 沿航向反方向摆几个圆出来是一串分立圆点，像毛虫不像拖尾；
  真拖尾得沿路径画一条渐细的带状多边形。这个功能默认关闭（`TrailGhosts = 0`）。
- **⚠ 碰撞用的空间哈希，格子边长必须 ≥ 判定距离，否则就"要贴上走一段才触发"。**
  本项目踩过：哈希格子边长取的是 `BigMinRadius`(50)，而大球的判定距离是 `r_a + r_b`
  = **107~150 格**，远超"3×3 邻域保证能找到"的 50。后果是两颗球**深深重叠之后**才被判成碰撞 ——
  一帧里被推开几十格（很突兀），玩家感受就是"接触了一段距离才触发"。
  教训是**规模假设用错了地方**：哈希那套 O(n) 是为上万颗小球准备的，可小球根本不参与碰撞。
  现在改成**直接两两枚举大球**（先收下标再双重循环）：大球同时在场只有 10~15 颗，
  ~100 次距离判断比维护一张表还便宜，而且**精确、不会漏判**。
  参考实现（商业版 `BallManager.ProcessBigBallCollisions`）就是这么做的，注释写得很直白：
  "收集所有大球的索引，避免遍历小球"。`Game/SpatialHash.cs` 随之删除。
  **同类坑在参考项目里也有**：`ComputeShaderBattleSimulation` 的格子 5、3×3 邻域只覆盖 15，
  而 `attack_range` 是 20 —— 它的文档自己承认漏检，理由是"下一帧会因为位置变化而补上"。
  三方对比与通用公式见 **`docs/reference-comparison.md`**。
- **⚠ 同队连射会"出生即重叠"。** 大球每 1.2 秒一发、速度 90 格/秒 ⇒ 前一发已经飞出
  **108 格**，而判定距离是 107~150 格 —— 摆角稍小一点，新球就**出生在上一颗身上**，
  一帧被推开几十格。这在实测里占"深度重叠"的绝大多数（同队、靠近炮口、两颗都偏大，
  因为判定距离大于 108 才可能重叠）。修法：发射前检查炮口，**被占住就先不打**
  （能量留着、计时也不重置）。实测代价：大球实际发射量是额定值的 **86~90%** ——
  被挡时等的不是几十毫秒，而是**等前一颗偏航/撞墙为止**（同向等速的两颗球间距不会自己变大）。
  另外给分离量加了**每帧上限**（`MaxSeparationPerStep = 6` 格）兜底：
  正常重叠 ≤3 格根本碰不到它，深度重叠也不会再一帧瞬移。
- **⚠ 弹性碰撞的"正在接近"判定极易写反，写反了表现是"粘着"而不是"不碰撞"。**
  法线 `n` 是从 b 指向 a 的单位向量，所以两颗球的**距离变化率 = (v_a − v_b)·n = an − bn**，
  接近就是 **`an < bn`**。本项目一度写成 `an > bn`，后果是**接近时一次都不改航向** ——
  球只会被"把重叠量对半推开"那点位移慢慢挤开，看起来就是**粘在一起、几乎不反弹**
  （用户反馈原话："吸附一样很小的反弹""有种粘着感觉"）。
  实测：改前 22 次重叠只有 7 次改了航向、**平均偏转 1.4°~6.2°**；
  改成 `an < bn` 后 8~11 次重叠里 7~11 次改航向、**平均偏转 67°~85°**
  （正面对撞是 180°）。这种 bug 不会报错、也不会崩，只会让手感"说不出的黏"。
- **大球的描边宽度别用宽渐变。** 一开始颜色和透明度共用一个宽区间（`smoothstep(0.30, 0.95)`），
  结果实心环占了外侧四成，看起来是一圈粗环。现在两者分开：颜色用窄区间、
  透明度用宽区间。环带太窄也不行 —— 半径 1.5 格（屏幕上约 2px）时环只有 0.35px，整颗球会消失。

## 3. 想调节奏就动这几个旋钮

| 目标 | 旋钮 |
| --- | --- |
| 收敛更快 | `BaseHitPoints` ↓（现 8000）、`BaseDamagePerSecond` ↑（小球秒伤，现 30）、`BigBallBaseDamageScale` ↑（大球倍率，现 12） |
| 大球能磨多深 | `CostRampSeconds` / `MaxCellCost`（现 25 / 16）—— ⚠ 每格成本现在**只作用于大球**（小球走生命），所以这就是"大球推进深度"的主闸门 |
| 大球出膛能量范围 | `BigBallEnergyMin` / `BigBallEnergyMax`（现 6000 / 30000）—— 摇的范围，决定大小分层与"这颗能推多远"。⚠ Min 必须 ≥ `BigBallEnergy`(4000) |
| 大球大小范围 | 由能量范围推出来：半径 = 50 + 50×√插值，6000→53、30000→75、80000→100 |
| 大球更常见 / 更稀有 | `BigShotInterval` ↑ / ↓（现 1.2 秒；大球一直在场上滚，所以在场数 ≈ 存活时长 ÷ 它） |
| 大球互撞更痛 / 更轻 | `BigBallClashEnergyCost`（现 1500，敌对各掉一份） |
| 大球活得更久 / 更短 | `BallUpkeepPerSecond` ↑ / ↓（现 120/秒；不回能，所以这就是"纯挂机寿命"的总闸门） |
| 小球大小 | `SmallRadius`（现 **2.0**，恒定）。⚠ 半径同时是判定宽度：改了要**连着改 `SmallBallCellLifeCost`**（半径翻倍 ⇒ 每步扫过的新格子翻倍 ⇒ 成本要减半，射程才不变） |
| 球更多 / 更少 | 小球改 `SmallBallLifetime` / `TurretFireInterval`；大球改 `MaxBalls` 与 `BigShotInterval` |
| 小球推得多深 | `SmallBallCellLifeCost` ↑ / ↓（现 0.025 秒/格 = 40 格 1 秒生命） |

## 4. 当前的玩法数值

| 项 | 值 |
| --- | --- |
| 地图 | 1000×1000 = 100 万格。**全程无中立**：开局按"离哪个基地最近"切成四个象限；某家出局时它的地盘按同样规则分给最近的幸存者 |
| 势力 | 4 家，各占一个角（顺时针：左上 → 右上 → 右下 → 左下），基地内缩 9% |
| 基地 | 判定半径 = `Team.BaseRadius(14) × BaseSizeScale(3)` = 42；炮口距离一起缩放 |
| 炮塔 | 摆动着齐射：每 0.4 秒一轮、每轮 24 颗、散布 ±17°、摆动 ±43°，各队相位错开 |
| 弹珠半径 | **两段式**：能量 < 4000 → 恒定 **1.0**（不随能量变化）；能量 ≥ 4000 → 在 **50 ~ 100** 之间随 √能量 增长 |
| 小球 | **固定能量的子弹**：能量冻结，不扣维持费、不回收；半径恒定 **2.0**；时间每秒扣 1 秒生命（总预算 **16 秒**），**踩敌方格每格再扣 0.025 秒生命**（40 格 = 1 秒），生命 ≤0 销毁 |
| 大球 | **只由炮塔打出来**（每座每 1.2 秒一颗）。**出膛能量随机摇**：`[BigBallEnergyMin, BigBallEnergyMax]` = `[6000, 30000]` → 半径约 53~75，摇到多少就是它这辈子的全部预算。**能量只减不增**（没有回能）。**直线横推 + 撞墙反弹 + 撞球反弹**；**压进敌境是逐格磨，没有一次性爆炸** |
| 大球碰撞 | 撞上就**弹开**（等质量弹性碰撞：交换法线方向的速度分量）。⚠ 判定用 **`an < bn`**（接近），写反过一次 → 变成"粘着"，见坑清单。同队只弹不掉能量；**敌对各掉 `BigBallClashEnergyCost`(1500)** —— 不是"谁大谁赢、小的消失" |
| 增殖来源 | ~~增殖门~~ → ~~自家领土补给~~ → **两者都删了**。大球的强弱完全由出膛那一次随机决定 |
| 小球寿命 / 敌境成本 | 时间 **16 秒**：`16 × 90 = 1440` 格 ≥ 对角线 1414 格（`1000√2`），所以**任意直线路径都飞得完**，时间不构成射程闸门。敌方格 **0.025 秒/格**（40 格 = 1 秒）—— 半径 2 的盘每步扫过约 6 格、即每秒 360 格，**每秒额外烧 9 秒生命**（合计约 10 倍流失），满生命的球进纯敌境只撑约 1.6 秒 |
| 小球视觉尺寸 | 世界半径 2 格 ⇒ 直径 4 格。默认缩放（fit ≈ 0.72）下屏幕上约 2.9 px；`RadiusOf × 2` 就是着色器 quad 的边长 |
| 每格占领成本 | 1 → 16（每 25 秒 +1，`CostRampSeconds = 25`；⚠ **只作用于大球**，小球走生命池）。这就是"大球能磨多深"的主闸门 |
| 增殖来源 | **自家领土补给**：大球站在本方领土上每秒 +2500 能量（原来靠增殖门，已删除）。**只对大球生效**，小球能量是冻结的 |
| 小球的出生能量 / 维持费 | 2000（固定）/ 大球每秒 120 |
| ~~释放门槛~~ | ~~能量 3000、抽 60%、半径 40、攻击力 255~~ **按需求整体删除（"不要爆炸"）**，见下方"大球压进敌境" |
| 增殖门 | ~~32 个，半径 55，冷却 4 秒，×2 与 ×4 混合~~ **已删除；后来替代它的"自家领土补给"也已删除** |
| 大球判定 | 半径 ≥ 50（= `BigMinRadius`，也就是"小球 / 大球"的分界线本身） |
| 小球透明度 | `SmallBallAlpha = 0.42` |
| 能量数字 | 能量 ≥ 4500 且在前 24 名内才显示，压在球正中央。**阈值必须高于大球门槛 4000**，否则会出现"一串数字挂在小点上"。字号 **16 px**（屏幕像素，不随缩放变）、黑描边 5 px、盒子高 21 px。格式：千进位 K / 百万 M，最多一位小数（`6.2K` / `80K` / `1.5M`） |
| 辉光 | intensity 0.55、threshold 1.15、hdr_scale 3.0、luminance_cap 1.5，高位 `glow_levels/3..7` 全 0 |
| 碰撞 | **不用空间哈希**：只有大球互撞，而大球同时在场 10~15 颗，直接两两枚举（~100 次距离判断）更便宜也更准 |
| 最大实例数 | `MaxBalls = 8000`（缓冲 8000 × 16 × 4 = 512 KB/帧，整块上传） |

### 尺寸参数

- **基地**：`BaseSizeScale = 3`，同时缩放判定半径、炮口距离、护盾环标识。
  炮口距离一起缩放是必须的 —— 只放大基地的话炮口会埋进球里，射出来的球直接从护盾内冒出来。
- **大球**：走 `BigMinRadius` / `BigMaxRadius`（现 50 / 100）这对绝对半径，
  不再是"倍数 × 基础曲线"。原因见上面"半径改成了两段式"。

⚠ `MaxRadius` 必须 ≥ `BigMaxRadius`，否则大球会被削平。
（历史上这里还有一条"碰撞网格边长"的取舍 —— 已经随空间哈希一起删掉了，
因为那个"取舍"本身就是漏洞的来源，见坑清单第一条。）

### 两档球各有一个「生命池」，扣的来源是同一条：时间 + 敌方格

- **小球**（能量 < 4000）：生命池就是**剩余寿命**（`SmallBallLifetime` 秒）。能量冻结
  —— 不扣维持费、不回收。**时间每秒 −1 秒**；
  **每涂掉一格敌方格 −`SmallBallCellLifeCost`(0.025) 秒**；生命 ≤0 销毁。
  ⚠ 寿命（16 秒）是**时间预算的上限，不是射程** —— 定它的标准是"别让时间成为闸门"
  （对角 1414 格 ÷ 90 格/秒 = 15.7 秒 ⇒ 取 16 秒）。真正决定"能推多远"的是敌方格那一项。
- **大球**（能量 ≥ 4000）：生命池就是**能量**。时间通过维持费 −120/秒；敌方格每格
  −`cellCost`；敌对碰撞再各 −`ClashEnergyCost`；**没有任何回能**；跌破 4000 就**降级**
  成小球（半径掉回 1.0，环消失）并拿到一段新的小球寿命，跌破 `MinEnergy`(100) 才销毁。
  **唯一来源是炮塔的蓄力射击**（`BigShotInterval` + 随机出膛能量），出场半径约 53~75。

两边的"生命"存的东西不同（秒 / 能量），但**规则是同一条**，所以调平衡时看的是同一个问题：
"时间和敌方格各自要收多少，才能让它推到自己该停的地方"。

⚠ `Paint` 里 `isBig` **一次算好、整趟复用**：能量在循环里会被扣，如果逐格重新判断，
一颗球扣到中途跨过 `BigBallEnergy` 就会前半程扣能量、后半程扣生命 —— 一脚踩两只船。
另外"每格只收一次"不是靠记账，而是靠**上一步已经把它染成自己的了**（同阵营格子直接跳过）。
所以只有**染不动**的格子（对方强度 > 攻击力）才会每步反复收钱 —— 那正是"撞墙被磨死"。

实测对比（同一打法，稳态）：

| | 敌境涂色免费、寿命 8 秒 | 敌境每格扣 0.025 秒、寿命 16 秒、半径 2（现） |
| --- | --- | --- |
| 弹珠数 | ~1950 | **~1000**（27 秒内 927~1148 波动） |
| 画面 | 各阵营长条状色带横穿整张地图 | 四个角落的领土完整，中段是一圈**拉锯的毛边**，色带只在中场交叠 |
| 染色 / 碰撞 | 0.26 / 0.10 ms/步 | 0.16~0.24 / 0.09 ms/步，FPS 315~367 |
| 平均寿命 | 8 秒（射程 720 格） | **约 4.6 秒** —— 16 秒的预算基本用不完，都是死在敌境里 |

最后一行是关键：**16 秒的时间预算几乎从不成为死因**（否则弹珠数会是 240×16 = 3840），
实际死因全是"敌境扣光生命"。所以这两个数各管一件事：
**寿命决定"时间不会先杀它"，敌境成本决定"它推得到多远"**。

小球那一档还留着一条老关系：**人口 = 射速 × 存活时长**（现在多一层自平衡 —— 敌境越长、
球死得越快、人口越低）。两个旋钮都是 `[Export]`，在检查器里改一个数就能调，不用重编：
`SmallBallLifetime`（时间那份）、`SmallBallCellLifeCost`（敌方格那份）。

这个改动连带修了三处，每一处都是实测撞出来的：

1. **基地秒伤是按球累加的。** 小球以前会因烧能量快速减员，改成"免费涂色 + 寿命制"之后
   上千颗小球长期在场、一窝蜂压到基地上 —— `BaseDamagePerSecond = 1500` 时
   10 颗球贴身就是 15000/s，**整局 16 秒就打完**。现在降到 30/s，大球另给 12 倍。
2. **大球不能被小球撞死。** 旧碰撞规则是"赢家掉输家那份能量"，一颗 2000 能量的小球撞上
   6000 的大球就能啃掉 2000 —— 三次就把它打回小球档。所以小球被排除在碰撞之外
   （互相穿透，当子弹用）。
   **后来大球之间也换了规则**：不再是"谁大谁赢、小的直接消失"，而是**弹开 + 双方各掉一份能量**
   （`ClashEnergyCost`）。这样大球互撞是互相消耗，而不是一颗无声吞掉另一颗。
3. **大球压进敌境的那套判定（现已随释放机制删除，教训保留）**：两个独立的坑：
   - 只看**球心**那一格：半径 48 的球压在边界上时球心还在自家地盘、盘子另一半已盖住敌境，
     → 判定不出来，而它又要为那半边敌境逐格付钱，能量瞬间跌破门槛。
   - 只要"分次付"就必须保证一次付到底：只按比例抽 60% 的话，一颗 30000 能量的球抽完还剩
     12000、仍然过线，于是贴着敌境的每一步都要再付一次（30000→12000→4800→1920）。

**"1.5 秒解除保险"（`BigBallArmTime`）已删除 —— 它只剩副作用。**
那段窗口是配套"一次性爆炸"加的：出膛第一步踩到敌境就会自爆，所以先让它光飞 1.5 秒不染色。
释放删掉之后，它唯一的效果就是**"大球扫过敌方领土却不填色"** —— 玩家一眼就能看出来
（实测：球心还在敌境上的大球，几乎每次都正好在这 1.5 秒窗口里；因为窗口一结束，它要么
一步把走廊染成自己的、要么 1~2 秒内被敌境烧穿掉回小球档，都不再"站在敌境上"）。
对照实验（把窗口设 0，出膛即染）：大球数量 **5~14**，和保留 1.5 秒时（7~14）没有区别 ——
它本来就是在自己地盘上出膛的，而自家格子不收费。删掉后采样里"球心在敌境"恒为 0，
也就是**能看到的大球都在边飞边填**。

实测稳态（新一轮设计：随机出膛能量 + 无回能 + 弹开）：弹珠约 **1000~1180**、
**大球常驻 10~15 颗**、染色 0.26~0.59 / 碰撞 0.07~0.17 ms/步、FPS 217~313。
大球对每格的开销实测**易主率 77~100%** —— 它付了钱的格子基本都真的变成自己的。

### 大球：随机能量 + 直线横推 + 撞球弹开 + 不回能

一轮按需求做的整体改动，四条互相关联：

| 需求 | 实现 | 备注 |
| --- | --- | --- |
| 出膛时决定自身随机能量、不同能量不同大小 | `TickBigShots` 在 `[BigBallEnergyMin, BigBallEnergyMax]` 里摇一个数，炮塔按摇出来的数扣能量池 | `[6000, 30000]` → 半径 53~75。想更极端就抬 `BigBallEnergyMax`（80000 → 半径 100） |
| 能量只消耗、不增加 | 删掉 `OwnLandRegen` 与整段回能代码（`IsOnForeignLand` 随之删除） | 出膛摇到的数就是**一辈子**的预算 |
| 直接横推 | 大球**不再随机抖航向**（`TurnRate` 只作用于小球） | 出膛定死方向 ⇒ 玩家能预判它去哪，这对"花本钱打出来的东西"很重要 |
| 撞墙 / 撞球反弹 | 撞墙沿用 `BounceOffWalls`；撞球用**等质量弹性碰撞**：只交换法线方向的速度分量（台球那套），重叠量对半推开（**每帧封顶 6 格**） | **直接两两枚举大球，不用空间哈希** —— 大球只有 10~15 颗，哈希反而会漏判（见坑清单）。⚠ "接近"判定是 `an < bn` |
| 遇敌方大球减能量 | 敌对各 −`ClashEnergyCost`(1500)，**带 0.4 秒冷却**（擦身而过会连续几十帧重叠，逐帧扣会把一次接触算成几十次）；**不掉血、不吞噬、不判谁赢** | 同队只弹、不掉能量 |

实测：反弹 1~7 次/4 秒、敌对碰撞 0~20 次/4 秒、大球数量稳定在 10~15（**没有堆积**，
说明它们最终都会在敌境里磨掉预算）。画面上最直观的变化是**大球有明显的大小分层**
（29.7K 的环比 10.8K 的大一圈），而且因为不再随机拐弯，它们推出来的走廊是笔直的。

⚠ 唯一的代价：大球活得比旧版久（旧版一碰边界就炸/立刻降级），
所以染色耗时从 0.17~0.27 涨到 **0.26~0.59 ms/步**（每个大球每步都要过一遍 7250 格的盘），
FPS 从 278~339 降到 **217~313**。要压回来就减 `BigShotInterval` 的产出（调大间隔）。

⚠ **删掉释放之后凸出来的新问题：大球变成了唯一的主力攻城武器，而且它比原来强太多。**
原来一颗大球在敌境只能炸一个半径 40 的圆（约 5000 格）；现在它是一路磨过去，
实测能推进 100~300 格、留下 `96 × 250 ≈ 24000` 格（≈ 全图 2.4%）的走廊 —— **约 5 倍**。
于是出现了正反馈：磨下的地 → 自家补给面积变大 → 大球更能长、活更久 → 磨得更多。
实测 27.6 秒时领土是 **42.8 / 25.5 / 16.9 / 14.8**，一边倒（有释放时同一时刻是 29.8 / 26.6 / 22.4 / 21.2）。
压它的旋钮就是 `CostRampSeconds` / `MaxCellCost`（每格成本现在**只作用于大球**）。

### 增殖来源的两次删除（增殖门 → 自家领土补给 → 都没有了）

原来地图上撒 32 个增殖门，弹珠滚进去能量翻倍 —— 这是题材名字里 "Multiply" 的那一半。
后来删掉门，改成**站在本方领土上每秒回能**（`OwnLandRegen`，一度 260、后来 2500）——
理由是"大球是靠能量活着的，能量只减不增就没有续航"。

**再后来这一条也删了**（需求：能量只消耗、不增加）：大球的强弱改成完全由
**出膛那一次随机**决定，出膛摇到的数就是它一辈子的预算。
所以现在这个项目里**没有任何能量回复途径** —— 增殖门、自家领土补给，都没有了。

⚠ 这条历史值得记的是**它如何反转了一个取舍**：能量只减不增时，`BigBallRadius` 阈值必须压在
出生半径以下才看得见大球；改成会增长之后，阈值放到出生半径以上才有区分度（从 2.8 改成 4.5）。
现在又回到"不回能"，但**阈值不需要改回去** —— 因为半径曲线已经换成两段式
（小球恒定 1.0 / 大球 50~100），阈值的作用变成了"小球 / 大球的分界线"本身。

原来 `ReleaseTeam` 把地盘全变回中立，现在改成**按"离哪个还活着的基地最近"分给幸存者**，
于是地图上永远不会出现中立区域。

用最近基地而不是"全给击杀者"，是为了不让一次爆冷直接滚成雪球；分给最近的两家，
战线才会自然地向空出来的那块推进。实测淘汰后 `中立` 仍然是 0。

### 渲染：不加特效

有一轮做过"炫酷效果"（领土边界辉光、大球能量漩涡、炮塔蜂窝网格 + 扫描线 + 蓄力闪光、
释放冲击波），后来按需求**全部删掉**；之后又试过一轮"加强边界辉光"，也**再次删掉**
（领土被打碎成细条时边界格占比极高，整片区域一起发光，糊成一片惨白）。现在只剩静态外观：

| 形态 | 画法 |
| --- | --- |
| 小球 | 阵营色 + 半透明（`SmallBallAlpha`） |
| 地图 | 纯调色板查表值，经 `Map.gdshader` 直通输出（采样器声明 `filter_nearest`） |
| 大球 | 纯黑内核 + 一圈极细阵营色环（环带 `0.93~1.0`，占半径 **7%**） |
| 炮塔基地 | 实心核心 + **紧贴核心**的护盾环（`0.505~0.575`） |

实例只用到：颜色 rgb = 阵营色、a = 透明度、自定义 x = kind。
**kind 只有三个值：0 小球 / 1 大球 / 2 基地**（不留空号）。

**采样一律 nearest，而且是双重保险。**

- 节点层：项目默认（`rendering/textures/canvas_textures/default_texture_filter=0`）和
  MapLayer 本来就是 nearest，但球层和标记层只是"继承默认值"，所以代码里把三层的
  `TextureFilter` 都显式钉死（`ConfigureSampling`）—— 编辑器会覆盖场景文件。
- 着色器层：地图走 `Shaders/Map.gdshader`，里面用**自定义采样器**声明
  `uniform sampler2D map_texture : filter_nearest, repeat_disable;`。
  内建的 `TEXTURE` 没法挂过滤器提示（过滤方式只能由 `CanvasItem.texture_filter` 决定），
  换成自己的采样器才能把 nearest 写死在着色器里 —— 这样即使节点属性被改回线性，
  领土边界也不会发糊。该着色器是纯直通，不改变任何颜色。

⚠ **基地的护盾环不在四边形边缘。** 四边形边长是 `BaseRadius × 4.2`，所以着色器里的
`dist 0.5` 才对应基地的真实半径（实心核心画到那儿，正好和判定半径对齐），
护盾紧贴在外面一点（`0.505~0.575`）。一开始把它画在四边形边缘（`0.955~1.0`），
结果它落在半径 88 格处 —— 看起来是个孤零零飘在基地外面一大圈的环。
**改四边形那个 4.2 倍必须同步改着色器里 kind == 2 的三个区间。**

⚠ **环带变窄时，最外圈那层抗锯齿必须一起收窄。** `edge` 原来从 0.94 开始淡出（吃掉外侧 6%），
环带收到 7% 时会被它吃掉大半；现在 `edge` 只处理最外 2%。

留两条实测数据，免得以后重走：

- **地图着色器里做边界检测非常贵。** 判定边界要采样八邻域 = 每像素 9 次纹理采样，
  实测帧率从 **347 掉到 123**。改成在 CPU 端做（`Palette.ToRgba` 本来就逐格扫全图，
  顺手比 8 个邻居）能把帧率救回 **225**，代价是调色板转换从 0.4ms 涨到 1.15ms。
  即便这样也不划算 —— 最终整个删掉了。
- **`Environment.SetGlowLevel` 的 idx 是 0 起的**（idx 0 对应界面上的 `glow_levels/1`）。
  写成 `1..7` 会把第 2~7 级全打开，那是最宽范围的模糊，**整屏被糊成一片惨白**。

**另一条经验**：大面积、低饱和度的填充图形会被读成"无主地"。增殖门原来画成
半径 55、alpha 0.75 的实心半透明圆饼，32 个铺满全图，被当成"地图上还有中立区域"
反馈了两次。表示"可交互的点位"要用只有轮廓的画法，中间留空。
### 半径改成了两段式（小球恒定 2.0 / 大球 50~100）

```csharp
if (energy < BigBallEnergy(4000)) return SmallRadius(2.0);          // 小球：恒定，不随能量变化
t = (√energy − √4000) / (√80000 − √4000);                          // 大球：用 √能量 插值
return 50 + 50 × clamp(t, 0, 1);                                    // 50 ~ 100
```

**"变大"这件事本身就等于"晋级成大球"** —— 小球永远只有一种大小，攒够 4000 能量直接跳进
大球档，之后才继续长。中间没有连续过渡，这是刻意的。

用 √能量 而不是能量本身做插值：前段涨得快、后段放缓，符合"刚晋级时最有存在感"的直觉。

**一个自然带出来的对比**：半径同时是判定宽度，**每一步的消耗 ≈ 盘宽 × 速度 × 每格成本**。
小球半径 1 的涂色盘只有几个格子，在敌境上烧钱极慢、活得久；大球半径 48，每步要为新盖到的
上百格付钱，一进敌境就烧得飞快。所以"小球耐活、大球脆"不需要额外设计。

实测：前 17 秒全场 `半径max=1.0`；t=20s 首批 6 颗晋级（最小半径正好 30.0）；
t=32s 到 60 颗、半径峰值 34.1 且持续增长；中立 0；弹珠约 1200；FPS 285-314。

⚠ 这里以前还有一条"碰撞网格边长按 `BigMinRadius(50)` 取、代价是巨球偶尔漏判一次碰撞"的取舍 ——
**那个"偶尔"其实是系统性的**：判定距离 107~150 远超格子边长，碰撞要深深重叠才触发。
小球本来就不参与碰撞，所以整张哈希表都是多余的，现在改成直接两两枚举大球。

### 炮塔射速是弹珠数量唯一的闸门

改成"四角炮塔发射"之后，弹珠数量不再由收入决定（收入永远过剩），而是由
**射速 × 存活时长**决定。⚠ 存活时长的上限是 `SmallBallLifetime`，
但**实际寿命由敌境的消耗决定**，所以下面这行数不是"射速 × 寿命"：

| 每轮颗数 | 寿命 | 敌境成本 | 实测弹珠数 |
| --- | --- | --- | --- |
| 10 | 8s | 免费 | ~550（画面太稀） |
| 24 | 8s | 免费 | ~1300 |
| 24 | 6s | 免费 | ~1465 |
| 24 | 6s | 0.02 秒/格 | ~1009 |
| 24 | 16s | 0.05 秒/格 | ~1000（927~1148） |

⚠ 但**能量仍是硬约束**：一轮消耗 `LaunchEnergy × TurretBallsPerShot`，
必须小于 `本方领土格数 × IncomePerCell × TurretFireInterval`。
否则炮塔会持续哑火 —— 表现为"射速明明调高了却没球"，而且不会报错。
丢地盘会直接反映成火力下降，这是这个设计好的地方。
